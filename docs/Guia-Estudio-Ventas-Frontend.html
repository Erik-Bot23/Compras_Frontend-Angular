2. Glosario de conceptos base

Conceptos que aparecen una y otra vez en el código. Léelos antes de la bitácora: ahí se aplican con ejemplos reales.

2.1 Componente standalone

Angular 21 no usa NgModules. Cada componente declara lo que necesita en el arreglo imports de su decorador @Component. Así no hay una "mochila" global de imports y el lazy loading es más limpio.

@Component({
  selector: 'app-salehistory',
  imports: [CommonModule, FormsModule, Sidebar, PaginatePipe, PaginationControl],
  templateUrl: './salehistory.html',
  styleUrl: './salehistory.css',
})
export class Salehistory implements OnInit { /* ... */ }
Punto clave Si un template falla con NG0303: Can't bind to 'ngForOf' o similar, casi siempre falta importar CommonModule (directivas ngIf/ngFor, pipes date, number) o FormsModule (ngModel).

2.2 Observable vs BehaviorSubject

Un Observable es un flujo de datos al que te suscribes. Un BehaviorSubject es un observable especial que guarda el último valor y lo entrega de inmediato a quien se suscribe. Eso lo hace ideal para estado compartido.

// Estado compartido del menú lateral (singleton providedIn: 'root')
private menuOpen$ = new BehaviorSubject<boolean>(true);
menuOpen = this.menuOpen$;   // se expone como Observable de solo lectura
toggle(v: boolean) { this.menuOpen$.next(v); }

El carrito del POS (CobroService) también usa BehaviorSubject<CobroItem[]>: cada componente que se suscribe ve el carrito actual y todos los cambios siguientes.

2.3 subscribe y change detection

HttpClient.get() devuelve un observable frío: hay que .subscribe() para disparar el request. El callback next recibe la respuesta.

this.saleService.getSales().subscribe({
  next: (data) => { this.sales = data; this.loading = false; },
  error: () => { this.loading = false; }
});
Aquí está la razón de reactivar zone.js (sección 3.2) En apps zoneless, asignar this.sales = data dentro del callback NO redibuja la tabla sola: Angular no sabe que "algo cambió". zone.js parchea XMLHttpRequest/fetch y avisa a Angular para que corra la detección de cambios al terminar cada request.

2.4 Pipes

Un pipe transforma un dato en el template. Los "puros" (por defecto) solo recalculan cuando cambia la referencia de entrada.

  • {{ total | number:'1.2-2' }} — formato numérico: mínimo 1 entero, 2 decimales.
  • {{ fecha | date:'dd/MM/yyyy HH:mm' }} — formato de fecha.
  • {{ lista | paginate: page : pageSize }} — pipe propio que recorta la lista.

2.5 ng-container y ng-template

<ng-container> agrupa elementos sin generar un nodo en el DOM. Es la forma idiomática de repetir varias filas por cada elemento de un *ngFor sin envolverlas (lo que rompería la tabla HTML).

2.6 Data binding

2.7 Guard funcional (CanActivateFn)

Función que decide si se puede entrar a una ruta. En este proyecto valida route.data.permission contra los permisos del usuario en localStorage.

// app.routes.ts
{ path: 'compras', component: Compras, canActivate: [permissionGuard],
  data: { permission: 'VER_COMPRAS' } }

2.8 Directiva estructural *hasPermission

Oculta/muestra UI según permisos sin tocar los components. Uso: *hasPermission="'CREAR_COMPRAS'". Es la contraparte de los guards a nivel de fragmento.

2.9 Interceptor HTTP funcional

Se ejecuta en cada request/response. Aquí agrega el token y maneja el 401 global.

// Agrega Authorization: Bearer <token> y, ante un 401, limpia sesión y va a '/'
intercept(req, next) {
  const token = safeGetItem('token');
  const authReq = token ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }) : req;
  return next(authReq).pipe(catchError(err => { /* 401 → logout */ }));
}

2.10 SSR-safe: guard de window

En SSR/prerender no existe localStorage ni window. Los helpers envuelven el acceso para que el build de Netlify/nginx no explote.

export function safeGetItem(key: string): string | null {
  if (typeof window === 'undefined') return null;
  try { return window.localStorage.getItem(key); } catch { return null; }
}

3.1 Imágenes de productos (2026-09-09) ok

Problema

Las imágenes de productos no se veían porque el backend devolvía rutas relativas o null y el frontend las usaba tal cual.

Razonamiento

El origen de la imagen puede cambiar (localhost → Railway). Si la URL es relativa, hay que completarla contra environment.api; si es absoluta, respetarla. Así las imágenes sobreviven al cambio de dominio sin tocar el backend.

Solución

// productos.ts — imageUrl()
imageUrl(p): string {
  if (!p.img) return 'assets/placeholder.png';
  return /^https?:\/\//.test(p.img) ? p.img : `${environment.api}${p.img}`;
}
Concepto /^https?:\/\//.test(x) es una expresión regular que comprueba si el string empieza por http:// o https://.

3.2.1 SidebarService (estado compartido del menú)

  • Problema: cada componente tenía su menuOpen local; al navegar el menú no se sincronizaba.
  • Solución: un singleton (providedIn: 'root') con menuOpen$ y suscripción a router.events.
  • Detalle fino: se escucha NavigationStart (no NavigationEnd) para que el cierre empiece al hacer clic y la animación de 800ms alcance a terminar antes de cargar el componente nuevo.
this.router.events
  .pipe(filter(e => e instanceof NavigationStart))
  .subscribe(() => this.toggle(false));

3.2.2 Reactivación de zone.js (el bug más importante)

Síntoma Las tablas y el estado de caja no aparecían hasta que el usuario hacía clic en algún lado. La petición HTTP sí llegaba, pero la vista no se actualizaba.

Causa raíz: Angular 21 usa zoneless por defecto. Sin zone.js, los callbacks de HttpClient.subscribe() no disparan detección de cambios.

Fix (3 pasos):

npm install zone.js @angular/ssr@21.2.1

// angular.json
"polyfills": ["zone.js"]

// app.config.ts
providers: [ provideZoneChangeDetection(), /* ... */ ]
Concepto: change detection Angular debe saber cuándo revisar los bindings. Zoneless depende de signals o de markForCheck(); con zone.js, Angular intercepta eventos y async y revisa solo. Se reactivó porque el proyecto usa RxJS + *ngFor clásicos.

3.3 Seguridad + preparación de despliegue (2026-09-12) ok

3.3.1 storage-utils.ts (helpers SSR-safe)

Centraliza el acceso a localStorage y evita errores en SSR/prerender y ante un localStorage manipulado.

export function safeGetItem(key: string): string | null {
  if (typeof window === 'undefined') return null;      // SSR/prerender
  try { return window.localStorage.getItem(key); }
  catch { return null; }                                // contexto restringido / JSON roto
}

3.3.2 isLogged() valida la expiración del JWT

Antes bastaba con que existiera un token; si estaba expirado la app se veía "logeada" pero todo fallaba. Ahora se decodifica el payload (claim exp) y se rechaza el token vencido.

Concepto: JWT Un JWT son 3 partes separadas por punto: header.payload.signature. El payload va en Base64 y contiene claims como exp (expiración, en segundos Unix). El frontend puede LEERLO para saber si expiró, pero no puede validar la firma: eso es del backend.

3.3.3 AuthInterceptor: 401 global

Si el backend responde 401, el interceptor limpia la sesión y redirige a /. Excluye /auth/login, forgot-password y reset-password, porque ahí un 401 es un fallo de credenciales normal, no una sesión vencida.

3.4 Paginación client-side (2026-09-12) ok

Razonamiento

Los servicios ya cargan TODOS los registros. En vez de tocar el backend, se pagina en memoria: más simple, instantáneo, sin endpoints nuevos. El precio es que no escala a miles de filas (ahí sí habría que paginar en servidor).

Solución

// core/pipes/paginate/paginate.ts (pipe PURO, standalone)
transform(list: T[], page: number, pageSize: number): T[] {
  const start = page * pageSize;
  return list.slice(start, start + pageSize);   // clampa si la página quedó fuera de rango
}

// template
<tr *ngFor="let p of filteredProducts | paginate: page : pageSize"> ... </tr>
<app-pagination [total]="filteredProducts.length" [pageSize]="pageSize"
                [page]="page" (pageChange)="page = $event"></app-pagination>
¿Por qué el pipe clampa? Si borras el último ítem de una página, page puede quedar fuera de rango y la tabla se vería vacía. El pipe ajusta la página al último índice válido.

Decisión: el carrito del POS NO se pagina — es un carrito vivo, no una tabla de registros.

3.5 Filtros client-side (2026-09-12) ok

Patrón

Estado de filtro en el componente + un getter que devuelve la lista filtrada. El *ngFor y el [total] de la paginación usan la lista filtrada, así el pie cuenta solo lo visible.

// componentes CRUD
selectedCategory: number | null = null;   // null = "Todas"

get filteredProducts(): Product[] {
  if (this.selectedCategory === null) return this.products;
  return this.products.filter(p => p.categoryId === this.selectedCategory);
}

// al cambiar el criterio, volver a la primera página
onCategoryFilterChange() { this.page = 0; }
Trampa resuelta con [ngValue] <option [value]="p.id"> entrega el string "3", pero el getter compara p.categoryId === 3 (número). Con [ngValue]="p.id" el select entrega un number real y la comparación estricta funciona. Igual con booleanos (Activo/Inactivo) en Usuarios.

La barra usa clases compartidas en styles.css: .table-filter-bar, .table-filter-field, .filter-select, .filter-input. Va como primer hijo de .table-card, con el mismo lenguaje visual que el pie de paginación.

3.6.2 Filtros client-side en Salehistory (fechas + método)

fromDate = '';
toDate = '';
selectedMethod: PaymentMethod | null = null;

get filteredSales(): SaleHistory[] {
  let result = this.sales;
  if (this.selectedMethod !== null) {
    result = result.filter(s => s.paymentMethod === this.selectedMethod);
  }
  if (this.fromDate || this.toDate) {
    result = result.filter(s => {
      const datePart = s.saleDate.substring(0, 10);   // 'yyyy-MM-dd'
      if (this.fromDate && datePart < this.fromDate) return false;
      if (this.toDate   && datePart > this.toDate)   return false;
      return true;
    });
  }
  return result;
}
Truco: comparar fechas como strings saleDate viene como ISO (2026-09-15T10:30:00). Al cortar los primeros 10 caracteres queda 2026-09-15. Como ese formato es yyyy-MM-dd, comparar con < / > es equivalente a comparar cronológicamente y es inmune a timezones (a diferencia de new Date(), que puede correr el día).

3.7 Botones Editar/Cancelar unificados (2026-09-15) ok

Problema

Cada CRUD tenía su propio estilo de botón "Editar": productos/usuarios usaban amarillo; categorías usaba class="editRole" (clase que ni existía → botón sin estilo); roles usaba .editRole azul sólido. Además solo categorías mostraba botón Cancelar al editar.

Razonamiento

Un lenguaje visual consistente reduce carga cognitiva: el usuario aprende una vez que amarillo = editar, rojo = eliminar, gris = cancelar. Se eligió .cancel gris (no rojo) para no confundir cancelar-edición con eliminar-registro.

Solución

  • Categorías y roles pasan a class="edit".
  • Se agrega Cancelar en edición a productos, usuarios y roles: <button *ngIf="editingXId" class="cancel" (click)="cancelEdit()">Cancelar</button>. El *ngIf hace que solo aparezca en modo edición.
  • Nueva clase .cancel (gris #64748b → #475569) en los 4 CSS.
/* Lenguaje de botones de acción, igual en los 4 CRUDs */
.edit   { background: linear-gradient(135deg, #facc15, #eab308); } /* amarillo */
.delete { background: linear-gradient(135deg, #ef4444, #dc2626); } /* rojo   */
.cancel { background: linear-gradient(135deg, #64748b, #475569); } /* gris   */
// productos.ts — estado de edición + cancelar
editingProductId: number | null = null;

editProduct(p: ProductForm) { this.editingProductId = p.id ?? null; /* ... */ }
resetForm()                  { this.editingProductId = null; /* ... */ }

// salehistory.ts — resumen reactivo de lo filtrado
get filteredCount(): number { return this.filteredSales.length; }
get filteredTotal(): number {
  return this.filteredSales.reduce((sum, s) => sum + (s.total ?? 0), 0);
}
Getters como "computed" sin signals Un getter se recalcula cada ciclo de detección: simple pero no gratis. Para listas pequeñas (historial paginado) es perfecto. Con listas grandes convendría memoizar o usar computed() de signals.

3.8.3 Compras: tabs, detalle en fila completa, botones y estados vacíos

  • Tabs: de botones sueltos a control segmentado (contenedor #1e293b, .tab.active azul #2563eb + sombra).
  • Botones: .editRole → .edit; los "Cancelar" pasan de .delete (rojo) a .cancel (gris).
  • Detalle expandible: antes era un <div> dentro de la celda de acciones (columna angosta). Ahora es una fila completa con colspan="5".
  • Estados vacíos en las 3 tablas + prop loading.
  • Montos con | number:'1.2-2'; botón primario verde → azul.
<!-- ng-container agrupa las dos <tr> por compra sin inyectar nodos al DOM -->
<ng-container *ngFor="let c of filteredPurchases | paginate: page : pageSize">
  <tr>
    <td>{{ c.purchaseDate | date:'dd/MM/yyyy HH:mm' }}</td>
    <td class="money">{{ c.total | number:'1.2-2' }}</td>
    <td><button class="view" (click)="toggleDetalle(c.id)">Detalle</button></td>
  </tr>

  <!-- Fila de detalle: ocupa toda la tabla con colspan -->
  <tr *ngIf="detalleAbiertaIds.has(c.id)" class="detalle-row">
    <td colspan="5">
      <div class="detalle fade-in"> ... subtabla ... </div>
    </td>
  </tr>
</ng-container>
Por qué <ng-container> y no un <div> Dentro de <tbody> solo pueden ir <tr>. Un <div> rompería el HTML. <ng-container> permite repetir dos filas hermanas lógicamente agrupadas sin generar un elemento real.

El estado de expansión se guarda en un Set<number>:

detalleAbiertaIds = new Set<number>();
detalleAbiertaIds.has(id)   // ¿está abierto?
toggleDetalle(id: number) { /* agrega/quita del Set */ }

Estado vacío con mensaje diferenciado — clave para debugging de filtros:

<tr *ngIf="!loading && filteredPurchases.length === 0">
  <td colspan="5" class="empty-row">
    {{ purchases.length === 0
        ? 'No hay compras registradas'
        : 'No hay compras que coincidan con el filtro' }}
  </td>
</tr>
Lección de UX Distinguir "no hay datos" de "los filtros no arrojan nada" evita que el usuario crea que se borraron los registros. El mismo patrón se usó en Salehistory.

  • Tarjetas resumen: barra de acento superior con ::before por métrica (.accent-blue Ventas, .accent-green Total vendido, .accent-orange Ticket promedio), montos con $ y subtítulos descriptivos.
  • Gráficas: cada header lleva un .chart-dot con el color de la serie en Chart.js → leyenda visual sin mirar la gráfica.
  • Corte de caja: montos con $ y tabular-nums; .card alineada a .table-card.
/* Barra de acento superior: pseudo-elemento, sin HTML extra */
.card { position: relative; overflow: hidden; }
.card::before {
  content: ''; position: absolute; top: 0; left: 0; right: 0; height: 3px;
  background: var(--accent, #2563eb);
}
.card.accent-blue   { --accent: #3b82f6; }
.card.accent-green  { --accent: #22c55e; }
.card.accent-orange { --accent: #f97316; }
Custom properties (variables CSS) Se define --accent en la clase de cada tarjeta y el ::before la usa. Es DRY: la regla de dibujo se escribe una vez y cada tarjeta solo cambia el color.
